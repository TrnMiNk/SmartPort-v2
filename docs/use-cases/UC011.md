# UC011 — Cập nhật và vô hiệu hóa hồ sơ tàu

**Status:** Completed (2026-11-18; evidence in `docs/testing/phase-a-b-evidence.md` §4) · **Module:** M1 · **Priority:** H · **Rollout:** Đợt 1
Source: `usecases.txt` lines 2015–2055. FR-VES-01; NFR-USA-01, NFR-SEC-04.

## 1. Objective
Search vessels, update their data, deactivate vessels no longer in service, and see every change.

## 2. Actors
- **Primary:** Điều phối viên.
- **Supporting:** Quản trị hệ thống (read).

## 3. Permissions (SRS matrix, enforced by the API)
- Search and read (`GET /ships`, `/ships/:id`, `/ships/:id/history`): `view` on M1 (`BAN_QUAN_LY`, `DIEU_PHOI_VIEN`, `NHAN_VIEN_KHO_BAI`, `QUAN_TRI_HE_THONG`); agents see only their own agents' vessels (404 for others).
- Update and deactivate: `DIEU_PHOI_VIEN` only. Every other role gets 403, audited as DENIED.

## 4. Preconditions
The vessel exists (UC-010); the user holds the permission.

## 5. Postconditions
- **Success:** data updated or vessel deactivated; one audit row with old and new values, actor, time and reason; revision +1.
- **Failure:** no change.

## 6. Main flow
1. The coordinator searches by IMO (prefix) or name (`GET /ships?search=`), ten per page.
2. The list shows matches; the vessel name opens its detail page with change history.
3. The coordinator chooses "Edit" or "Deactivate".
4. The form (or a dialog asking for a reason) is shown.
5. The coordinator saves or confirms. The request carries the revision read earlier (`If-Match`).
6. The API validates, saves, and writes the audit row.

## 7. Alternative flows
- **2a. No match:** "Không có dữ liệu".
- **5a. IMO changed to an existing IMO:** `409`, error under the IMO field.
- **5b. The record changed meanwhile:** `409`; the screen reloads the newest data into the form and asks the user to check and save again.
- **5c. No field changed:** the form refuses locally ("Không có thay đổi nào để lưu").

## 8. Exception flows
- **6a. Deactivating a vessel with an unfinished voyage:** refused with `BUSINESS_RULE_VIOLATION` (`SHIP_HAS_UNFINISHED_VOYAGE`), naming the voyages, until the voyage ends.

## 9. Business rules
- **BR-1** A deactivated vessel cannot receive new arrival notices (UC-013) and is hidden from the default list and from the notice form.
- **BR-2** Every change to the vessel record is recorded with old and new values.
- **BR-3** A voyage is unfinished unless its status is `DEPARTED` or `REJECTED`.
- **BR-4** Deactivation requires a reason (1 to 500 characters).
- **BR-5** Updates are optimistic: the revision must match.

## 10. Acceptance criteria
- AC-1 The history shows every change (who, when, why, old to new). **Passed.**
- AC-2 A deactivated vessel cannot be chosen when creating an arrival notice. **Passed.**
- AC-3 Deactivation with an unfinished voyage is refused. **Passed.**
Evidence: `docs/testing/phase-a-b-evidence.md` §4.

## 11. Assumptions
| ID | Assumption | Rationale |
|---|---|---|
| A-1 | History is read from the generic `audit_events` table; the legacy `ship_audit_log` is not created. Refused attempts are audited but not shown in the history. | Rule 04: one audit record shape. |
| A-2 | "Unfinished" means any status other than `DEPARTED` or `REJECTED`. | A rejected voyage never finishes, so counting it would block deactivation forever. A voyage waiting for documents (`MISSING_DOCUMENTS`) can be resubmitted, so it counts. |
| A-3 | Deactivation needs a reason; an edit reason is optional. | Rule 04 asks for a reason on significant state changes; the specification names none. |
| A-4 | Editing an inactive vessel is allowed; reactivation is not offered. | The specification does not mention it. |
| A-5 | A vessel cannot be deleted. | Not in the specification. |

## 12. Demo scenario
1. Edit a vessel's name with a reason, open its detail page. Expect "Updated · date · actor — reason" and "Name: old → new".
2. Deactivate a vessel with an announced voyage. Expect refusal naming the voyage; after the voyage is rejected, expect success.
