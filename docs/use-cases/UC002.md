# UC002 — Đăng xuất & quản lý phiên làm việc

**Status:** Completed (2026-11-18, evidence in `docs/testing/uc001-uc002-evidence.md`) · **Module:** Chung (dependency) · **Priority:** H · **Rollout:** Đợt 1
Source: `usecases.txt` lines 1648–1685. FR-ADM-01; NFR-SEC-02, NFR-SEC-05.

## 1. Objective
End a session and make its token unusable at once. Sessions expire after a period of inactivity.

## 2. Actors
- **Primary:** any authenticated user.
- **Supporting:** authentication service.

## 3. Permissions
Any authenticated user may log out their own session. No other role is needed.

## 4. Preconditions
- The user has a valid session (UC-001).

## 5. Postconditions
- **Success:** the session is revoked; the cookie is cleared; the next request with the old token returns 401; the event is audited.
- **Failure:** the session is unchanged.

## 6. Main flow
1. The user chooses "Đăng xuất" (`DELETE /api/v1/auth/logout`).
2. The API revokes the session row (`revoked_at`).
3. The API clears the cookie and returns `204`.
4. The API audits `LOGOUT`.

## 7. Alternative flows
- **2a. Logout called twice:** the second call returns `204`; the audit reason is `ALREADY_REVOKED`.
- **Inactivity:** a session with no request for 30 minutes (sliding) is refused as expired.

## 8. Exception flows
- **4a. The token cannot be revoked (network error or server error):** the browser session is cleared by deleting the readable presence marker `sp_auth`; the API refuses a session without it. The user is sent to login with an explanatory notice. The server token is not revoked and expires by time (idle 30 minutes). A client error such as 403 is not treated this way: the page stays and shows the error.
- **Unconfirmed unsaved data (spec step 2):** frontend responsibility; not enforced by the API.

## 9. Business rules
- **BR-1** A revoked token is not accepted on any later request.
- **BR-2** Idle sessions expire after 30 minutes by default (`SP_SESSION_IDLE_MINUTES`). Each accepted request extends the expiry (sliding).
- **BR-3** Only the token hash is stored; a database read does not reveal a usable token.

## 10. Acceptance criteria
- AC-1 After logout, the old token gets 401 on the next request. **Passed** (API integration; browser e2e replays the captured cookie against the server).
- AC-2 A forged token gets 401. **Passed** (API integration).
- AC-3 Inactivity expiry after 30 minutes (sliding). **Passed** with a limit: expiry past and the sliding extension are tested against stored timestamps in SQL Server (API integration) and the browser shows the expiry notice (e2e). A real 30-minute wait was not run.
- AC-4 The frontend returns to the login page after logout. **Passed** (browser e2e, also at a 390 px width).

## 11. Assumptions and deviations
| ID | Item | Rationale | Affected |
|---|---|---|---|
| A-1 | Expiry is sliding: each accepted request extends it. The specification says "hết thời gian không hoạt động" (idle), which supports sliding. | Matches "no activity" wording. | BR-2 |
| A-2 | Absolute session lifetime is not set. | The specification does not define one. A maximum lifetime is a recommended addition, not in scope. | BR-2 |
| A-3 | **Resolved 2026-11-18:** specification exception 4a is implemented with a second, readable cookie (`sp_auth`) that the API requires together with the HttpOnly `sp_session`. Deleting it signs this browser out without revoking the token. | The HttpOnly cookie cannot be deleted by script; the marker makes the specified behavior possible. | Section 8 |
| A-4 | The marker is not a secret and not a security control; it records that this browser chose to sign out. A stolen token is still protected only by its confidentiality and expiry. | Honest limit of the design. | Section 8 |
| A-5 | The frontend can delete the marker only when it shares the cookie host with the API (same host or a shared parent domain). Different registrable domains need a deployment decision. | Cookies are scoped by host. | Section 8 |

## 12. Demo scenario
1. Log in, then log out. Expect 204 and the cookie cleared.
2. Replay the old cookie against `/api/v1/auth/me`. Expect 401.

## 13. Test coverage
- API integration (SQL Server): `auth.http.test.js` (logout revocation, forged token, expired session, sliding timeout).
- Frontend unit: `Front/test/unit/auth.test.js` (logout success, already signed out, network failure keeps the session).
- Browser e2e: `Front/test/e2e/auth.e2e.test.js` (logout and protected pages, failed logout banner, expiry notice, narrow-screen regression).

## 14. Status reasoning
All four acceptance criteria passed with recorded evidence, so the UC is **Completed**. Limits: the 30-minute idle expiry was simulated by timestamps (not waited), and spec step 2 (confirm sign-out with unsaved data) does not apply yet because no dashboard form holds editable data.

## 15. Exception 4a (resolved)
Earlier in this slice the page stayed and showed an error, which differed from the specification. It now follows the specification: the browser session is cleared and the token expires by time (A-3, A-4, A-5). Evidence: `auth.test.js` (offline and 5xx clear the marker, 403 does not), `auth.http` (token without marker is refused; with marker still valid), `auth.e2e` "UC-002 4a" (see `docs/testing/phase-a-b-evidence.md` §3). An intermittent e2e timeout seen twice is described in §5 of that file.
