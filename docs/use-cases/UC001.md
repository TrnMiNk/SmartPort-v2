# UC001 — Đăng nhập hệ thống

**Status:** Completed (2026-11-18; evidence in `docs/testing/phase-a-b-evidence.md` §2) · **Module:** Chung (dependency) · **Priority:** H · **Rollout:** Đợt 1
Source: `runtime-verification/final-acceptance/usecases.txt` lines 1606–1646. FR-ADM-01; NFR-SEC-01, -02, -05, NFR-USA-01.

## 1. Objective
Authenticate a user by username and password and open a session. Every other use case depends on it.

## 2. Actors
- **Primary:** any user.
- **Supporting:** authentication and authorization service (in the API).

## 3. Permissions
Public endpoint. No role required.

## 4. Preconditions
- The account exists and is active.

## 5. Postconditions
- **Success:** a server-side session exists; the response carries the user's roles; the event is audited.
- **Failure:** no session; generic error; failed-attempt counter updated.

## 6. Main flow
1. The user submits username and password (`POST /api/v1/auth/login`).
2. The API validates the input shape (`validation/authValidation.js`).
3. The API verifies the password against the stored scrypt hash.
4. The API creates a session and sets the `sp_session` cookie.
5. The API returns the user and roles. The frontend routes by role.

## 7. Alternative flows
- **4a. Wrong username or password:** `401 INVALID_CREDENTIALS` with the same message for both cases. The counter is incremented only when the account exists.

## 8. Exception flows
- **4b. Account inactive:** `403 ACCOUNT_INACTIVE`. Audited as `DENIED`.
- **4c. Five consecutive failures:** `423 ACCOUNT_LOCKED` on the fifth failure; the account stays locked for the configured duration. Audited as `FAILED` with `LOCKED_AFTER_FAILURES`.
- **Locked account, correct password:** `423` (the lock is checked before the password).
- **Database error:** `500 INTERNAL_ERROR`, no detail.

## 9. Business rules
- **BR-1** Passwords are never stored or returned in clear text. Stored as scrypt with a per-password salt (`security/password.js`).
- **BR-2** Five consecutive failures lock the account (UC-001 business rule, configurable: `SP_LOGIN_MAX_FAILURES`).
- **BR-3** A successful login resets the failure counter.
- **BR-4** Every attempt is audited (success, failure, denial), with actor and reason.

## 10. Acceptance criteria
Results are in `docs/testing/phase-a-b-evidence.md` §2 (earlier results: `docs/testing/uc001-uc002-evidence.md`).
- AC-1 A user with the correct role sees only the permitted menu. **Passed.** The SRS permission matrix (section 2.2) gives the role-to-module rights; the API computes `permissions` from the roles and enforces them on every vessel and notice endpoint; the menu shows only pages whose module the role may view. Verified in the browser for six roles. Interpretation A-5 and A-6 (UC005) apply.
- AC-2 The account is locked after exactly five consecutive failures, for 15 minutes, and counting restarts after the lock. **Passed** (API integration and browser e2e).
- AC-3 Wrong credentials and unknown users get the same message. **Passed** (API integration and browser e2e).
- AC-4 Passwords are not logged or returned. **Passed** (unit, API integration, browser e2e: nothing secret in page, storage or DOM; cookie is HttpOnly).

## 11. Assumptions and deviations
| ID | Item | Rationale | Affected |
|---|---|---|---|
| A-1 | **Deviation:** the specification says "token JWT". V2 uses an opaque server-side session in an HttpOnly cookie. | UC-002 requires revocation before expiry, which a stateless JWT cannot give without a denylist. The legacy FE contract uses cookies. | Section 5, UC-002 |
| A-2 | **Lock duration is not in the specification.** 15 minutes, configurable (`SP_LOGIN_LOCK_MINUTES`). **Approved by the project owner on 2026-11-18** ("5 failed attempts, 15-minute lock"). | The specification says "khóa tạm thời" without a duration. | BR-2 |
| A-3 | **Changed 2026-11-18:** after the lock ends the failure count restarts, so five new failures are needed to lock again (it used to re-lock on the first failure). A correct login after the lock resets the counter. | Matches "5 failed attempts, 15-minute lock". Tested in `auth.http`. | BR-2 |
| A-4 | Unknown usernames are audited as `actor = anonymous` with reason `UNKNOWN_USER`. | Audit needs an actor. The attempted username is not stored to avoid writing attacker-chosen text. | BR-4 |

## 12. Demo scenario
1. Log in as an active coordinator. Expect 200 and the role list.
2. Enter a wrong password. Expect 401 with the generic message.
3. Repeat five times on one account. Expect 423 on the fifth.
4. Log in with the correct password while locked. Expect 423.

- Errors are shown in Vietnamese (API messages), as the specification requires; interface labels stay in English as in the imported design.
