## 1. Objective
The port manager approves a pending plan. The plan becomes approved, the berth is reserved for it, and the affected parties are notified.

## 2. Actors
- **Primary:** Ban quản lý (port management, decision D5).
- **Supporting:** Điều phối viên (submitter).

## 3. Permissions
- `BAN_QUAN_LY` only. Decision D5: the authorized Port Management role. Every approval is audited with the approver.

## 4. Preconditions
- The plan is `PENDING_APPROVAL` (UC-029).
- The approver holds `BAN_QUAN_LY`.

## 5. Postconditions
- **Success:** plan `APPROVED` with `approved_by` and `approved_at`; voyage prepared for berthing; in-app notifications to the agent and the coordinator; audit row.
- **Failure (rejected by the approver or constraints changed):** plan unchanged or moved to rejection (UC-031).

## 6. Main flow
1. The port manager opens the list of pending plans (`GET /api/v1/berth-plans?status=PENDING_APPROVAL`).
2. The port manager opens a plan and sees the check results, the AI proposal and any overrides.
3. The port manager chooses "Phê duyệt".
4. A confirmation dialog appears (frontend).
5. The port manager confirms (`POST /api/v1/berth-plans/:id/approve` with `confirm: true`).
6. The API re-runs the placement check at this moment (UC-026) and checks that no other approved plan overlaps.
7. The API sets the plan `APPROVED`, writes history, notifies the agent and coordinator, and audits.

## 7. Alternative flows
- **4a. The approver cancels the dialog:** the plan stays `PENDING_APPROVAL`.

## 8. Exception flows
- **6a. Constraints fail at approval (for example maintenance was added):** approval refused with the reason; the plan goes back for re-planning (UC-033, out of scope). The API returns `409 BUSINESS_RULE_VIOLATION` with the failing rule.
- **Caller without `BAN_QUAN_LY`:** `403 FORBIDDEN`, audited as `DENIED`.
- **Plan not pending:** `409`.

## 9. Business rules
- **BR-1** Approval requires `BAN_QUAN_LY` on the server. The frontend check is usability only.
- **BR-2** The check is repeated at approval. 100% of approved plans have no violation (spec acceptance).
- **BR-3** Approval and rejection are the only transitions to `APPROVED` and `REJECTED`.
- **BR-4 (decision F-4, 2026-11-19)** The approver is never the user who submitted the plan: 409 `SELF_APPROVAL` in the service (audited) and `CK_bp_no_self_approval` in the database.
- **BR-5 (decision F-1b)** A plan is approved only when its check passes **at the moment of approval**. An override reason lets a violating plan reach review (UC-029) but never makes a failed rule acceptable. Because BR-01 (overlap) and BR-03 (dangerous goods) are among the rules, they can never be approved while violated.
- **BR-6 (decision C-1)** Approval moves the voyage to `BERTH_ASSIGNED` and removes it from the waiting queue (queue positions behind it move up; the exit is kept in `voyage_queue_changes` as `LEFT_QUEUE`; the voyage keeps `queued_at` and its history).

## 10. Acceptance criteria
- AC-1 After approval, the affected parties are notified within 5 seconds. **Partly passed:** notices to the plan's submitter and to the users of the voyage's agent are written in the approval transaction (integration) and appear on an open page through the refresh channel (e2e, waited up to 8 s, not measured against 5 s). The yard, crane and gate notices are out of scope.
- AC-2 Approval is refused if a rule fails. **Passed:** the check is run again on current data inside the approval transaction; maintenance added, an approved overlap (BR-01), an out-of-service berth, dangerous or unverified cargo (BR-03) and changed ship data each give 409 `CONSTRAINT_VIOLATION_AT_APPROVAL`, the plan stays pending, the refusal is audited and the submitter is told. A stored `passed = true` is never trusted.
- AC-3 Only `BAN_QUAN_LY` can approve. **Passed:** coordinator, warehouse, agent and technician get 403 (audited DENIED); the approve button exists only for the permission `approve` and a forced call from the coordinator's page is refused.
- AC-4 Each approval is audited with the approver. **Passed:** `BERTH_PLAN_APPROVE` with the plan before and after, the decision (policy version, outcome, whether an override existed, the earlier result) and the voyage transition; refusals are FAILED rows with the rule.

## 12. Demo scenario
1. Port manager approves a pending plan. Expect `APPROVED`, berth reserved, notices sent.
2. Coordinator tries to approve. Expect 403.
3. Add maintenance over the planned time, then approve. Expect 409 with the rule.
