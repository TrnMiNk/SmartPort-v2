# UC031 — Từ chối kế hoạch cập bến

**Status:** Completed (2026-11-19). Every acceptance criterion and documented flow passed; AC-1 (reason within 5 s) measured in real browsers: 56 to 169 ms over 15 runs (B1, `docs/testing/a2-b1-realtime-evidence.md`). Evidence: `docs/testing/uc031-evidence.md`.
Source: `usecases.txt` lines 2823–2860. FR-BRT-07; NFR-USA-01, NFR-SEC-04.

## 1. Objective
The port manager rejects a pending plan with a reason. The plan returns to the coordinator; the berth is not reserved.

## 2. Actors
- **Primary:** Ban quản lý.
- **Supporting:** Điều phối viên.

## 3. Permissions
- `BAN_QUAN_LY`.

## 4. Preconditions
- The plan is `PENDING_APPROVAL` (UC-029).

## 5. Postconditions
- **Success:** plan `REJECTED` with reason; coordinator notified with the reason; audited.
- **Failure:** plan unchanged.

## 6. Main flow
1. The port manager opens the pending plan.
2. The port manager chooses "Từ chối".
3. The system asks for a reason.
4. The port manager enters the reason and confirms (`POST /api/v1/berth-plans/:id/reject`).
5. The API sets `REJECTED`, stores the reason, writes history and audit.
6. The coordinator is notified with the reason.

## 7. Alternative flows
- **4a. No reason:** rejection is not allowed.

## 8. Exception flows
- **5a. Plan already decided by someone else:** `409`; the current status is shown.

## 9. Business rules
- **BR-1** A reason is required (`CK_bp_reject_reason`).
- **BR-2** Rejection does not change berth state (the berth was never reserved).
- **BR-3** The previous plan, if any, stays in force until a new plan is approved (spec).

## 10. Acceptance criteria
- AC-1 The coordinator receives the reason within 5 seconds. **Passed:** the notice (with the reason) is written in the rejection transaction and appears on the dispatcher's open page within 5 s without reload (two-account browser scenario); it is visible only to the submitter.
- AC-2 A rejected plan does not change berth state. **Passed:** the berth stays "Trống", no plan reserves it, the voyage keeps its status and queue position, the queue is unchanged (integration and e2e).

## 11. Assumptions and open items
| ID | Item | Rationale | Affected |
|---|---|---|---|
| A-1 | A rejected plan stays in the database with status `REJECTED`. It is not reused. Re-planning creates a new plan. | Audit trail. | BR-3 |
| A-2 | "Returns the plan to the coordinator" means: the coordinator is told the reason and may make a **new** draft for the same voyage (the voyage stays WAITING_BERTH). The rejected plan is final: it cannot be approved, edited or resubmitted (409 `NOT_PENDING` or `NOT_DRAFT`). No new plan state was added. | The specification names only "Bị từ chối" and says the old plan is kept; resubmitting the same row is not described. | Postcondition |
| A-3 | Only `PENDING_APPROVAL` plans can be rejected; drafts, approved and completed plans answer 409 `NOT_PENDING` with the current status (5a). | Spec precondition. | Section 4 |
| A-4 | Who rejected, when and why is kept in the plan status history, the audit row (before and after, previous and new state) and `rejection_reason`; `berth_plans` has no rejector column and none was added. | History and audit already carry actor and time. | BR-1 |
| A-5 | The specification does not forbid a user who holds both roles from rejecting a plan they submitted (it only forbids approving). That is allowed. | Rejecting a own plan withdraws it and grants nothing. | Section 3 |
| A-6 | A rejection needs the permission `approve` on M2_BERTHS (`BAN_QUAN_LY`), the plan revision (`If-Match`) and a reason of 1 to 500 characters. | Spec BR and permissions; same lock order as approval. | BR-1 |

## 12. Demo scenario
1. Reject a pending plan without a reason. Expect refusal.
2. Reject with reason "không đủ cẩu bờ". Expect `REJECTED` and the coordinator's notice.
