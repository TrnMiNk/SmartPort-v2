# UC016 — Dự báo ETA bằng AI

**Status:** Implemented for the non-AI parts (2026-11-19): display, history, fallback, storage. NOT Completed: no real provider, no data, no model (section 16). Earlier status: Analyzed · **Module:** M1 (dependency, adapter only; provider pending D3) · **Priority:** H · **Rollout:** Đợt 1
Source: `usecases.txt` lines 2224–2262. FR-VES-05; NFR-PER-06, NFR-CMP-02, NFR-ACC-04.

## 1. Objective
Ask the AI service for an actual ETA for a voyage and show it next to the declared ETA, with deviation and confidence. Called by UC-015 and UC-018.

## 2. Actors
- **Primary:** AI service (external).
- **Supporting:** Điều phối viên (views the forecast history).

## 3. Permissions
- The call is made by the system during validation (UC-015). No direct user call is needed.
- Viewing the forecast history: `DIEU_PHOI_VIEN`, `BAN_QUAN_LY`.

## 4. Preconditions
- The voyage has a notice (UC-013) and has passed validation (UC-015), or its ETA was just updated (UC-018, out of scope).
- The AI service is configured (adapter address and timeout).

## 5. Postconditions
- **Success (`AVAILABLE`):** prediction stored with predicted ETA, deviation in hours, confidence in [0, 1], model version and input hash.
- **Failure (`UNAVAILABLE`):** stored with a failure reason; the voyage carries the label "chưa có dự báo AI".

## 6. Main flow
1. The system builds the request: vessel, origin port, speed, declared ETA (`POST` to the configured AI provider, path defined by the provider contract).
2. The AI service returns a predicted ETA and confidence.
3. The system computes deviation = predicted ETA − declared ETA, in hours.
4. The system stores the result as a new row in `voyage_eta_predictions` and points `voyages.latest_eta_prediction_id` at it.
5. The forecast is returned to the caller (UC-015) and shown beside the declared ETA.

## 7. Alternative flows
- **5a. Coordinator opens the forecast history:** all predictions for the voyage, newest first (spec step 5a).

## 8. Exception flows
- **2a. No response within `AI_TIMEOUT_MS` (10 000 ms) or error:** store `UNAVAILABLE` with the reason, log the failure (spec), continue with the declared ETA.
- **2b. Malformed AI response:** treated as `UNAVAILABLE` with reason `INVALID_RESPONSE`. Never stored as a forecast.

## 9. Business rules
- **BR-1** Deviation is in hours, ETA in ISO 8601 UTC (spec).
- **BR-2** A forecast is never simulated. Without a working provider the result is `UNAVAILABLE`.
- **BR-3** A stored `AVAILABLE` row must have a predicted ETA, confidence and model version (`CK_vep_result`).
- **BR-4** Predictions are append-only. The latest one is referenced from the voyage.

## 10. Acceptance criteria
- AC-1 Four values are shown together: declared ETA, predicted ETA, deviation, confidence. *(Frontend pending.)*
- AC-2 When the AI fails, the business flow continues with the declared ETA. **Evidence:** the `UNAVAILABLE` path is covered by schema test structure only; the flow test is pending.
- AC-3 **BLOCKED (D3):** a real forecast from a provider cannot be tested until a provider contract exists. This criterion is reported as **blocked**, not passed.

## 12. Demo scenario
1. With no provider configured, validate a voyage. Expect `ai.status = UNAVAILABLE` and the label "chưa có dự báo AI".
2. With a provider configured (later), validate again. Expect a stored forecast with deviation.

### 16.2 Display and history (what was built)
`GET /voyages/:id/eta-predictions` (newest first; each item: order number, request time, declared ETA at that time, status, predicted ETA, deviation, confidence with `confidence_meaning`, source `EXTERNAL_AI` with the model or `NONE` with the reason, input hash). `GET /voyages/:id` carries the latest as `eta`; the validation result `ai` carries the same fields and a replay shows the stored forecast instead of a blank. Scope: the coordinator and roles with view access, and an agent only for its own voyages (404 otherwise). No schema change: the existing columns were enough (the order number is computed). The vessels page shows the four values in the validation result and in the lifecycle dialog, plus the history table.

## 17. Asynchronous request and PENDING (2026-11-19)
The prediction is requested by a durable job after the notice is queued (UC015 section 17). A prediction now has three states: `PENDING` ("đang chờ dự báo AI"), `AVAILABLE` and `UNAVAILABLE` ("chưa có dự báo AI" with the reason). The history shows, for each prediction, the time, source, status, declared ETA, predicted ETA, deviation, confidence (only when it exists), and the **queue effect** (reordered, unchanged, not applied because the voyage left the queue, not applied because superseded, kept at a manual position). Screens: the result dialog and the lifecycle dialog show PENDING and update by themselves when the answer arrives; the queue tags a voyage "declared · AI pending", "declared" or "AI forecast". Evidence: `docs/testing/uc015-async-eta-evidence.md`.
