# UC023 — Xác nhận tàu rời bến

**Status:** Completed (2026-11-19). Every acceptance criterion and documented flow passed on SQL Server and in the browser. Evidence: `docs/testing/uc022-uc023-evidence.md`.
Source: `usecases.txt` lines 2500–2540. FR-VES-08, FR-BRT-10; NFR-PER-01, NFR-SEC-04.

## 1. Objective
Confirm that a vessel has left the berth. Record the actual departure time (ATD), move the voyage to `DEPARTED`, and release the berth.

## 2. Actors
- **Primary:** Điều phối viên.
- **Supporting:** Hệ thống.

## 3. Permissions
- `DIEU_PHOI_VIEN`.

## 4. Preconditions
- The voyage is `BERTHED` (UC-022).
- Billing clearance (UC-084) is **not** a precondition in this delivery (spec: "Từ Đợt 3").

## 5. Postconditions
- **Success:** ATD and actor recorded; voyage `DEPARTED`; berth released for the next vessel (no open interval after now); history row written.
- **Failure:** unchanged.

## 6. Main flow
1. The coordinator opens the voyage and chooses "Xác nhận rời bến".
2. The system checks that the voyage is `BERTHED`.
3. The form shows the actual departure time, defaulting to now.
4. The coordinator confirms (`POST /api/v1/voyages/:id/departure`).
5. The API records ATD and the actor, moves the voyage to `DEPARTED`, writes history.
6. The berth becomes free for later intervals; the queue and schedule refresh (UC-020, UC-021).

## 7. Alternative flows
- **3a. Coordinator edits the actual time:** a reason is required.

## 8. Exception flows
- **2a. Voyage not berthed:** refused (`409 BUSINESS_RULE_VIOLATION`).
- **4a. Concurrent change:** `409 CONFLICT`; reload.

## 9. Business rules
- **BR-1** ATD is not before ATA (`CK_voyages_atd`).
- **BR-2** The departure statuses in between (`WORKING`, `WORK_COMPLETE`, `PAID`) are skipped in this delivery (spec scope note).
- **BR-3** Berth release is derived, not stored (schema §4): departure completes the voyage's plan (`COMPLETED`, kept as history) and a completed plan holds the berth only until the actual departure time.

## 10. Acceptance criteria
- AC-1 After confirmation the voyage is `DEPARTED` with ATD and actor. **Passed** (integration, e2e; ATD before ATA refused).
- AC-2 The berth is free for later intervals. **Passed:** the berth shows Trống; another vessel can be planned and approved for the same stretch and time; another approved plan keeps it "Đã đặt trước"; a maintenance window shows "Bảo trì".
- AC-3 Each transition writes history. **Passed** (voyage history BERTHED>DEPARTED, plan history APPROVED>COMPLETED, audit `VOYAGE_DEPARTURE`).

## 11. Assumptions and open items
| ID | Item | Rationale | Affected |
|---|---|---|---|
| M-1 | Same edited-time rule as UC-022 (5 minutes of tolerance, reason when edited, future refused). | See UC-022 M-1. | 3a |
| M-5 | Departure completes the approved plan (`APPROVED` to `COMPLETED`, existing state; no new state or column). Overlap checks treat a completed plan as ending at the actual departure. The plan row is never deleted. | Lets the berth be reused as soon as the vessel leaves without losing history. | BR-3 |
| A-1 | Departure is allowed without billing clearance in this delivery. | Spec scope note for Đợt 1. | 4 |
| A-2 | `DEPARTED` is a state in the voyage lifecycle even though billing states are skipped. | Spec lifecycle lists "Đã rời cảng" as the final state. | BR-2 |

## 11a. API
`POST /api/v1/voyages/:id/departure`, permission M1 `edit` (coordinator only). Headers: `If-Match` (voyage revision, required). Body: `{ actual_time?, reason? }`. 200: voyage `DEPARTED` with `ata`, `atd`, `revision`, `plan_id`, `berth_id`, `atd_edited`. 400; 403 (audited); 404; 409 `NOT_BERTHED` (`voyage_status`) / `ATD_BEFORE_ATA` / `NO_APPROVED_PLAN` / stale (`current_revision`); 503 `BERTH_BUSY`. Service: `voyageMovementService.confirmDeparture`.

## 12. Demo scenario
1. Confirm departure of a berthed vessel. Expect `DEPARTED` and the berth free from now.
2. Try to depart a waiting vessel. Expect refusal.

## 13. Test coverage
- Integration (`voyage-movement.http.test.js`): main flow, checks, duplicates, 3 simultaneous departures, availability after departure, and one end-to-end chain through the real API only. Browser e2e: berthing then departure with two accounts. Results: `docs/testing/uc022-uc023-evidence.md`.

## 14. Status reasoning (historical, resolved 2026-11-19)
Not implemented. A voyage can only be BERTHED through UC-022, which is blocked (see UC022 section 14). Nothing in the product can produce the precondition, and the berth release is derived from approved plans (Module 2). The same open question about the state "Đã xếp bến" applies. Schema support exists (`atd`, `CK_voyages_atd`).
