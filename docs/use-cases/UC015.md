## 1. Objective

The system checks that a voyage notice is valid, calls the ETA forecast, and places valid voyages in the berth-waiting queue.

## 2. Actors

- **Primary:** Hệ thống (System).
- **Supporting:** Điều phối viên (Coordinator) — receives the notification and can trigger manual validation. Dịch vụ AI (AI service) — provides ETA forecast (UC-016).

## 3. Permissions

- Automatic validation runs as a continuation of an authorized intake (UC-013 or UC-014). It does not take a client-supplied operator key.
- Manual validation: coordinator session only. Legacy also requires loopback and an operator key; whether these carry into V2 is open (see A-6).
- Agent-owned voyages: an agent without ownership of the voyage cannot trigger or revalidate. **[assumption A-7]**
- Each agent may submit notices only for ships in its authorized scope (UC-014 business rule).

## 4. Preconditions

- The voyage notice was accepted by UC-013 (web) or UC-014 (partner API).
- The voyage is in status `Đã thông báo` (ANNOUNCED).

## 5. Postconditions

- **Success (VALID):** voyage is `Chờ cập bến` (WAITING_BERTH), in the queue, with a forecast ETA. Status history is written: Đã thông báo → Hồ sơ hợp lệ → Chờ cập bến.
- **Failure (MISSING_DOCUMENTS or REJECTED):** the reason is stored. The voyage is not in the queue and does not move to `Hồ sơ hợp lệ` or `Chờ cập bến`.

## 6. Main flow

1. System checks validity: required fields present, IMO format, vessel not on the prohibited or restricted list, documents still valid.
2. Result is `Hợp lệ` (VALID).
3. System calls the AI ETA forecast (UC-016).
4. System places the voyage in the berth-waiting queue by forecast ETA and priority.
5. System writes status history (Đã thông báo → Hồ sơ hợp lệ → Chờ cập bến).
6. System notifies the Coordinator.

## 7. Alternative flows

- **1a. Missing or wrong documents.** Result is `MISSING_DOCUMENTS`. Agent is notified to supply the documents. When the agent resubmits, the flow returns to step 1.
- **1b. Prohibited or restricted vessel, or documents expired.** Result is `REJECTED` with the reason. The flow ends.

## 8. Exception flows

- **3a. AI does not respond within 10 seconds.** Use the declared ETA, label the voyage "chưa có dự báo AI" (no AI forecast), continue at step 4. See assumption A-3.

## 9. Business rules

- **BR-1** Only VALID voyages enter the berth-waiting queue (BR-04, legacy spec).
- **BR-2** Every status change writes status history with time and actor (legacy spec).
- **BR-3** An invalid notice never enters the queue (acceptance criterion, legacy spec).
- **BR-4** Missing or invalid policy fails closed: no VALID result is produced without an effective policy. Legacy: 503 `VALIDATION_POLICY_UNAVAILABLE` (P1 doc). **[added]** from legacy implementation; confirm as requirement.
- **BR-5** Automatic validation for a demo-only environment is not available in production. Legacy: 403 `UC015_LOCAL_DEMO_ONLY`. **[added]** confirm.
- **BR-6** When a recheck fails, the voyage is removed from the queue and any cached AI forecast is cleared. **[added]** from legacy regression fix.

## 10. Requirements and acceptance criteria

**Traceability:** FR-VES-03, FR-VES-07, FR-VES-08; NFR-PER-01, NFR-PER-06 (legacy spec).

**Acceptance criteria (legacy spec):**
- AC-1: A valid voyage appears in the queue within 5 seconds of submission.
- AC-2: An invalid voyage never enters the queue.

**Added criteria [added] (rule 06 requires these; the legacy spec does not state them):**
- AC-3 **Determinism:** the same input and policy version produce the same outcome and the same reason.
- AC-4 **Audit:** each validation run writes one audit record with: input snapshot, policy version, each rule evaluated, outcome, and decision reason.
- AC-5 **No human confirmation** in the automatic business flow.
- AC-6 **Policy failure:** missing, invalid, or expired policy returns a policy-unavailable error and writes no VALID result, no queue entry, and no UC015 history.
- AC-7 **Infrastructure failure** (queue lock timeout, database error) is reported as an error, not converted to REJECTED or MISSING_DOCUMENTS. The notice remains ANNOUNCED.

## 12. Demo scenario (proposed; not in legacy spec) **[added]**

1. Create a voyage notice for an active vessel with valid approved documents and an effective policy. Expect: VALID, queued, status history with three steps.
2. Submit a notice for a vessel with a missing required document. Expect: MISSING_DOCUMENTS with reason. Not queued.
3. Submit a notice for a vessel on the restricted list. Expect: REJECTED with reason. Not queued.
4. Remove the effective policy, then submit a notice. Expect: policy-unavailable error. No VALID result, no queue entry.
5. Simulate an AI timeout. Expect: declared ETA used, label "chưa có dự báo AI", notice queued.

## 15. AI readiness (2026-11-19)
The AI part of UC-015 (step 3 and the queue by forecast ETA) depends on UC-016 and on a provider that does not exist. State today: the failure path (3a: declared ETA, label "chưa có dự báo AI", flow continues, error logged) is verified without a provider; the success path is **not verified**. The adapter now has a shared safe HTTP layer (timeout, optional key, size cap, one log line per call without secrets) and a validated contract. Gaps: no provider, no labelled data, no AIS or weather source, ATA in V2 is the berthing time and not the arrival time, UC-016 AC-1 (declared ETA, forecast, deviation and confidence together) is not met, and AC-1 (5 s) conflicts with a 10 s provider timeout in the slow-provider case. UC-015 stays **Implemented**; see `docs/architecture/ai-integration-readiness.md` (sections 2, 4, 5, 9).

### 16.2 The 5 s against 10 s conflict: options (needs a decision; nothing was changed)
1. **Asynchronous forecast:** queue the voyage at once with the declared ETA (AC-1 always met), call the provider after the commit, then store the forecast and re-sort the voyage in the queue. Cost: the queue position may change after entry and the UC-020 order rules must say how; step 4 "queue by predicted ETA" is then eventually true, not immediate.
2. **Shorter timeout on this path** (for example 4 s) while the 10 s of 3a and NFR-PER-06 stays for other uses. Cost: contradicts the 10 s wording of 3a.
3. **Amend AC-1:** "within 5 s when the AI answers within 3 s or is not configured; at most 10 s plus processing otherwise". Cost: a change of the SRS.
4. **Require the provider to answer within a stated bound** (an SLA for p99 below about 3 s). Cost: an external requirement; it does not help while the provider is down (10 s).
Recommended: option 1 (or 3 if the owner prefers not to change the queue semantics). Until one is approved UC-015 cannot be classified Completed.

### 16.3 Status
Stays **Implemented**: the conflict above is unresolved and the success path with a real AI forecast is unverified.

## 17. Asynchronous ETA (V2 design decision, 2026-11-19)
Evidence: `docs/testing/uc015-async-eta-evidence.md`. **A documented design decision subject to final SRS and business acceptance. UC-015 is NOT marked Completed.** This resolves the conflict of section 16.2 by option 1 (asynchronous forecast).

### 17.1 The changed flow
1. UC-015 steps 1, 2, 4, 5, 6 run in the request: deterministic validation, queue entry by the **declared ETA** and priority, history, notification. The response is immediate. **The AI provider is not called in the request.**
2. Step 3 (the forecast) is now a separate, durable job. With a provider configured, a `PENDING` prediction row is stored in the same transaction as the queue entry and the answer says `PENDING` ("đang chờ dự báo AI"). With no provider configured the answer is known at once: `UNAVAILABLE / NOT_CONFIGURED`, no job.
3. The ETA worker (`jobs/etaWorker.js`) claims the pending row, calls the provider (never longer than 10 s, UC-016 2a), stores `AVAILABLE` or `UNAVAILABLE` with the reason, and for a valid forecast moves the voyage in the queue (17.3). 3a is unchanged in effect: no answer within 10 s means the declared ETA keeps being used and the voyage keeps its place.
4. Screens refresh by themselves when the forecast arrives.

### 17.2 Acceptance
| # | Criterion | Status |
|---|---|---|
| A1 | AC-1: a valid voyage in the queue within 5 s, independent of the provider | **Passed with MOCK providers**: submission 25 to 38 ms against providers answering after 0.7 s, 5.5 s and never (10 s); browser 349 ms against a 1.5 s provider |
| A2 | 3a: provider silent for 10 s means declared ETA, flow continues | **Passed** (timeout recorded after about 10.06 s, queue unchanged) |
| A3 | Step 4: queue by forecast ETA and priority | **Passed** for the declared ETA at entry and for the reorder when a forecast arrives (priority tier kept, ties by entry time, positions 1..n) |
| A4 | Real AI forecast on the success path | **Not verified**: no provider |

### 17.3 Queue behaviour when a forecast arrives (under the queue lock)
The voyage must still be `WAITING_BERTH` (a voyage that left the queue, was berthed or departed is never touched and never put back; its approved plan is not read or changed: `NOT_APPLIED_LEFT_QUEUE`). The forecast must still be the voyage's latest (`NOT_APPLIED_SUPERSEDED`). A voyage a person moved by hand (UC-020) stays where the person put it (`KEPT_MANUAL_POSITION`). Otherwise the voyage takes the position the UC-020 order rules give its new effective ETA: priority first, then effective ETA, then entry time; the others keep their relative order and positions stay 1..n (`REORDERED` or `UNCHANGED`). Each move is recorded in the queue history (actor `system:eta`), in the audit log (`VOYAGE_ETA_PREDICTION`) and as a notice to the coordinators. The declared ETA and every earlier prediction are preserved.

### 17.4 Job reliability (supported configuration and limits)
The job is the database row (migration 0008). A claim is a lease (token and expiry on the database clock); claiming uses UPDLOCK and READPAST, so several workers never run one job at once. After a restart the pending row is still there and is claimed again once the lease ended (attempt 2). A late result from an expired claim and a repeated result are recognised by the token and ignored. A job claimed more than 3 times without finishing is closed as `UNAVAILABLE / ABANDONED` without calling the provider. **Supported and tested:** one API process (its worker), two workers racing on one database, a killed process. **Limits:** the refresh hint is in-process, so with several API processes only the clients of the process that stored the answer are told at once, the others see it on their next refresh; no dead-letter or retry-back-off policy beyond the 3 attempts; a lease is the provider timeout plus 15 s.

### 17.5 Assumptions and deviations (need approval)
| ID | Item |
|---|---|
| AE-1 | Step 3 happens after queue entry, so the first queue position uses the declared ETA. This deviates from the wording "queue by the forecast ETA" for the first placement; the forecast is applied afterwards. |
| AE-2 | A person's manual move of a voyage is respected: no automatic reorder of that voyage afterwards. |
| AE-3 | Only the voyage whose ETA changed is repositioned; the others are not re-sorted (manual moves of other voyages are not undone). |
| AE-4 | With no provider configured no job is created. |
| AE-5 | A job is abandoned after 3 claims; the lease is the 10 s limit plus 15 s. |
| AE-6 | The validation run keeps the AI status it had when it ran (`PENDING`); the final status is in the prediction history. |
