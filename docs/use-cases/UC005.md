# UC005 — Phân quyền theo vai trò (RBAC)

**Status:** Implemented for matrix and enforcement only (2026-11-18). The administration screen and role-change audit are out of scope, so it is not Completed · **Module:** Chung (dependency, minimal) · **Priority:** H · **Rollout:** Đợt 1
Source: `usecases.txt` lines 1775–1816. FR-ADM-03; NFR-SEC-02, NFR-SEC-04.

## 1. Objective
Assign roles to accounts and enforce them on the server. For this delivery only the enforcement part is needed. The admin screen is out of scope.

## 2. Actors
- **Primary:** Quản trị hệ thống (administrator).
- **Supporting:** authentication and authorization service.

## 3. Permissions
- Assigning roles: `QUAN_TRI_HE_THONG` only (screen out of scope).
- Enforcement: applies to every protected endpoint (default deny).
- **The matrix** is the SRS "Ma trận phân quyền tổng quát" (section 2.2), implemented in `API/src/security/permissions.js` and checked against the SRS in `API/test/unit/permissions.test.js`. X = view, T = create/edit, D = approve.

## 4. Preconditions
- The administrator is logged in (UC-001).
- The target account exists (UC-003, out of scope; seeded in this delivery).

## 5. Postconditions
- **Success:** role assignment saved; effective on the next request; audited.
- **Failure:** assignment unchanged.

## 6. Main flow (for this delivery: enforcement only)
1. An endpoint declares its allowed roles (`requireRole(...)`).
2. For each request the API loads the principal's current roles.
3. If none of the principal's roles is allowed, the API returns `403 FORBIDDEN`.

## 7. Alternative flows
- **Admin screen (spec steps 1–6):** out of scope for this delivery. Assignments are made by seed or script (`scripts/create-user.js`, `seeds/dev_seed.sql`).

## 8. Exception flows
- **An administrator tries to remove their own administrator role:** refused (spec 5a). Required when the screen is built; recorded as a requirement for the admin milestone.
- **Undefined permission:** denied (default deny).

## 9. Business rules
- **BR-1** Authorization is enforced on the server for every protected endpoint. Frontend hiding is usability only.
- **BR-2** Each change of roles is audited (spec). Scripted assignments are audited as `ACCOUNT_CREATED` by the provisioning service. **Gap:** the current `createUser` does not write an audit event yet. Open (see A-3).
- **BR-3** An account has one primary role in this delivery (spec 4: "mỗi tài khoản một vai trò chính"). The schema allows several roles; the one-role rule is not yet enforced.

## 10. Acceptance criteria
- AC-1 A user without the required role cannot access a restricted function (403). **Passed:** `permissions.test.js` (matrix equals the SRS, default deny), `vessels.http` authorization matrix over real endpoints, `vessels.e2e` (view-only role, technician, agent get 403 or 404 on forced calls).
- AC-2 Every role change is audited. **Not executed:** no administration path exists (out of scope); `createUser` still writes no audit row (A-3).
- AC-3 A role change applies on the next request. **Passed:** `auth.http` "UC-005 AC-3" (role granted and removed in SQL Server; `/me` reflects it at once, no new login).
