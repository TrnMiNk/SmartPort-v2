# UC020 — Xem và điều chỉnh hàng đợi cập bến

**Status:** Implemented (2026-11-18). Not Completed: the ordering assumptions Q-1..Q-3 are unapproved. Source: `usecases.txt` lines 2380–2418. FR-VES-07; NFR-PER-01, NFR-SEC-04.

## 1. Objective
Show the vessels waiting for a berth in queue order, and let the coordinator change an order with a reason.

## 2. Actors
- **Primary:** Điều phối viên.
- **Supporting:** Ban quản lý (views).

## 3. Permissions
- View: `DIEU_PHOI_VIEN`, `BAN_QUAN_LY`.
- Reorder: `DIEU_PHOI_VIEN`.

## 4. Preconditions
- At least one voyage is `WAITING_BERTH` (UC-015).

## 5. Postconditions
- **Success:** new position stored, reason stored, change recorded in `voyage_queue_changes`, other queue positions renumbered, M2 informed (refresh).
- **Failure:** order unchanged.

## 6. Main flow
1. The coordinator opens "Hàng đợi cập bến" (`GET /api/v1/voyages/queue`).
2. The list is sorted by queue position, showing predicted ETA and priority class.
3. The coordinator picks a voyage and chooses "Đổi thứ tự".
4. The system asks for a reason.
5. The coordinator enters a reason and confirms (`PATCH /api/v1/voyages/:id/queue-position`).
6. The API renumbers the queue, writes the change, and notifies M2 users (in-app, D6).

## 7. Alternative flows
- **5a. No reason entered:** the save button stays disabled; the API refuses with `VALIDATION_FAILED` if called directly.

## 8. Exception flows
- **6a. Concurrent change:** `409 CONFLICT` with the current queue; the coordinator reloads and repeats.

## 9. Business rules
- **BR-1** Only `WAITING_BERTH` voyages are in the queue; only validated voyages can enter (BR-04 in UC-015).
- **BR-2** Every reorder requires a non-blank reason (`CK_vqc_reason`).
- **BR-3** Positions are positive, unique and contiguous (renumbered on change).
- **BR-4** The queue is ordered by predicted ETA and priority class (FR-VES-07). Exact ordering rule: see A-1.

## 10. Acceptance criteria
- AC-1 Every reorder has a reason and an actor. **Evidence:** `voyage_queue_changes` constraints (schema). Endpoint pending.
- AC-2 The queue shows the correct order after a change. *(Pending.)*
- AC-3 A stale view is refused with `409` and reloads. *(Pending: needs `If-Match` on the voyage.)*

## 11. Assumptions and open items
| ID | Item | Rationale | Affected |
|---|---|---|---|
| A-1 | **Queue ordering rule is not defined.** The specification says "theo ETA dự báo và độ ưu tiên". Proposal: priority class first (`MAIN_LINE`, `REEFER_OR_HAZARD`, `STANDARD`), then predicted ETA (or declared ETA when no forecast), then queue time. | The specification names two keys but not their order. Needs approval. | BR-4 |
| A-2 | Ordering is applied on insert and on each change; positions are stored (not computed) so that a reorder is an explicit, audited change. | Keeps the reason and the before and after state. | BR-3 |

## 12. Demo scenario
1. Queue three vessels. Expect the order by the rule in A-1.
2. Move the last vessel to first with reason "tàu tuyến chính". Expect the change row and the new order.
3. Try to move without a reason. Expect refusal.

## 13a. Change from UC-030 (2026-11-19)
When a berth plan is approved the voyage becomes `BERTH_ASSIGNED` and leaves this queue: the positions behind it move up so the queue stays 1 to n, the queue revision changes (stale screens get 409 `QUEUE_CHANGED`), and the exit is recorded as a `LEFT_QUEUE` row in `voyage_queue_changes` with the voyage's earlier history intact. Tested in `docs/testing/uc029-uc030-evidence.md`.

## Update 2026-11-19: a forecast can reposition one voyage
When a valid ETA forecast arrives for a voyage that is still waiting, the ETA worker repositions that voyage with the order rules of this use case (priority first, effective ETA, entry time), under the queue lock, recording the move with actor `system:eta`. A voyage a coordinator moved by hand is not repositioned. See UC015 section 17.

## Update 2026-11-19: queue refresh
A manual move sends `QUEUE_MOVED {voyage_id}` after the commit; other open queues refresh within 59 ms (15 browser measurements). A hint is not proof of delivery: a page that missed it still gets 409 on a stale move (6a, tested by closing that page's channel). Evidence: `docs/testing/a2-b1-realtime-evidence.md`. Status unchanged.
