# UC022 — Xác nhận tàu cập bến

**Status:** Completed (2026-11-19). Every acceptance criterion and documented flow passed on SQL Server and in the browser. Evidence: `docs/testing/uc022-uc023-evidence.md`.
Source: `usecases.txt` lines 2458–2498. FR-VES-08; NFR-PER-01, NFR-SEC-04.

## 1. Objective
Confirm that a vessel has berthed. Record the actual berthing time (ATA), move the voyage to `BERTHED`, and mark the berth as in use.

## 2. Actors
- **Primary:** Điều phối viên.
- **Supporting:** Hệ thống.

## 3. Permissions
- `DIEU_PHOI_VIEN`.

## 4. Preconditions
- The voyage is `BERTH_ASSIGNED` (decision C-1; set when UC-030 approves the plan; the earlier wording "WAITING_BERTH" is superseded).
- An approved berth plan exists for the voyage (UC-030).

## 5. Postconditions
- **Success:** ATA and actor recorded; voyage `BERTHED`; the approved plan's berth shows as in use while now is inside its interval; history row written.
- **Failure:** unchanged.

## 6. Main flow
1. The coordinator opens the voyage and chooses "Xác nhận cập bến".
2. The form shows the actual time, defaulting to now.
3. The coordinator confirms (`POST /api/v1/voyages/:id/berthing`).
4. The API records ATA and the actor.
5. The API moves the voyage to `BERTHED` and writes the history.
6. The schedule shows the change (UC-021).

## 7. Alternative flows
- **2a. Coordinator edits the actual time:** a reason is required.

## 8. Exception flows
- **4a. The vessel is at a different berth from the approved plan:** refused with a warning; re-planning (UC-033) is required. **UC-033 is out of scope**, so this path refuses and tells the user to ask the port manager to re-plan.
- **5a. Concurrent change:** `409 CONFLICT`; reload and confirm again.
- **No approved plan:** refused (`409 BUSINESS_RULE_VIOLATION`).

## 9. Business rules
- **BR-1** ATA is recorded with the actor (FR-VES-08).
- **BR-2** Berth state is derived from plans and time (schema §4); no stored "in use" flag is written.
- **BR-3** Only `BERTH_ASSIGNED` voyages can be berthed (409 `NOT_BERTH_ASSIGNED` with the current status otherwise).

## 10. Acceptance criteria
- AC-1 After confirmation the berth shows "Đang sử dụng". **Passed** (integration; e2e: berth list on both accounts' open pages). Because the vessel is physically there, it is in use even if the plan interval is later or earlier than now (assumption M-3).
- AC-2 ATA is shown correctly. **Passed** (default now; edited time kept exactly; schedule bar source ACTUAL; lifecycle dialog).
- AC-3 Every transition writes history. **Passed** (`voyage_status_history` BERTH_ASSIGNED>BERTHED with actor; audit row `VOYAGE_BERTHING` with old and new state).

## 11a. API
`POST /api/v1/voyages/:id/berthing`, permission M1 `edit` (coordinator only; port management, warehouse, technician, agent are refused 403). Headers: `If-Match` (voyage revision, required). Body: `{ berth_id (required), actual_time? (ISO 8601 with zone), reason? (1 to 500) }`. 200: voyage `BERTHED` with `ata`, `revision`, `plan_id`, `berth_id`, `ata_edited`. 400 validation; 403 (audited); 404; 409 `NOT_BERTH_ASSIGNED` / `NO_APPROVED_PLAN` / `WRONG_BERTH` / `BERTH_OCCUPIED` / stale (`current_revision`); 503 `BERTH_BUSY`. Service: `voyageMovementService.confirmBerthing` (one transaction: berth lock, voyage lock, history, audit).

## 12. Demo scenario
1. Approve a plan (UC-030) for a waiting vessel. Confirm berthing. Expect `BERTHED`, ATA set.
2. Try to berth a vessel with no approved plan. Expect refusal.

## 13a. Decision C-1 (2026-11-19): settled, see `docs/architecture/m2-planning-design.md` §5.1 and §6

The precondition is now exact: the voyage is `BERTH_ASSIGNED` (set by the approval of the plan, UC-030). Confirming the berthing records the ATA and moves it to `BERTHED`. The database already accepts that transition (tested: `BERTHED` without an ATA is refused, with an ATA it is accepted, and the berth then shows `Đang sử dụng`). UC-022 itself is not built. The original analysis of the conflict follows.

### Original analysis

The state "Đã xếp bến" is analysed in `docs/architecture/m2-planning-design.md` §2. Summary: the specification sets the voyage to "Đã xếp bến" when the plan is approved (UC-030 step 6) and treats it as the starting state of UC-022 and UC-023, but the schema has no state between WAITING_BERTH and BERTHED, and BERTHED requires an ATA. The reading "an approved plan is the berth assignment, WAITING_BERTH stays until arrival, BERTHED is physical berthing" fits UC-021, UC-022 effects, UC-023 and UC-025, but contradicts UC-030 step 6 literally. It stays an open question for the business owner; no state was added.

## 14. Status reasoning (historical, resolved 2026-11-19)
Not implemented, because of two blockers that only Module 2 or a business decision can remove:
1. **No way to obtain the precondition. (Removed on 2026-11-19: UC-030 now produces `BERTH_ASSIGNED` voyages.)** An approved berth plan (UC-030) is created by Module 2. Without it the endpoint could only be exercised with hand-made rows, which would be a demo without a real workflow.
2. **The specification contradicts itself on the starting state.** `usecases.txt` says the precondition is the voyage "ở trạng thái Đã xếp bến" and the result is "cập nhật trạng thái theo vòng đời", and UC-023 starts from "Đã xếp bến" too. The lifecycle in UC-021 lists "Đã xếp bến" as a state between "Chờ cập bến" and the stages after berthing. Our schema has no such state (WAITING_BERTH then BERTHED). This record assumed WAITING_BERTH → BERTHED, but whether "Đã xếp bến" means plan approved (before arrival) or arrived is a business decision, and adding a state would invent a workflow state.
Schema support exists (`ata`, `CK_voyages_ata`). Ready to implement once Module 2 delivers UC-030 and the state question is answered.
