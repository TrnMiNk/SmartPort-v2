# UC025 — Theo dõi trạng thái cầu bến thời gian thực

**Status:** Implemented (2026-11-19). Not Completed: maintenance changes come from UC-034, which is not built; the refresh hints are in-process (one API process). AC-1 is now measured for the real events: after plan approval, berthing and departure the berth state changed in other browsers in 44 to 101 ms (B1, `docs/testing/a2-b1-realtime-evidence.md`). Evidence: `docs/testing/uc024-uc026-evidence.md`. · **Module:** M2 · **Priority:** H · **Rollout:** Đợt 1
Source: `usecases.txt` lines 2582–2617. FR-BRT-02; NFR-PER-04, NFR-PER-05.

## 1. Objective
Show each berth's state (Trống, Đang sử dụng, Bảo trì, Đã đặt trước) and refresh it within 5 seconds of an event, without a page reload.

## 2. Actors
- **Primary:** Điều phối viên.
- **Supporting:** Hệ thống (pushes updates).

## 3. Permissions
- `DIEU_PHOI_VIEN`, `BAN_QUAN_LY`.

## 4. Preconditions
- The berth catalog exists (UC-024).
- The user is logged in.

## 5. Postconditions
- **Success:** the displayed state matches the derived state at the time shown.
- **Failure (connection lost):** a warning "Dữ liệu có thể chưa cập nhật" is shown and the client reconnects.

## 6. Main flow
1. The coordinator opens "Cầu bến" (`GET /api/v1/berths/status`).
2. The screen shows each berth with its state.
3. An event (plan approved, vessel berthed or departed, maintenance set) changes the state.
4. The server sends a refresh hint on the realtime channel (`/api/v1/realtime/m2/events`).
5. The client re-reads the state and updates the screen.
6. The coordinator selects a berth to see the vessel, upcoming plans and maintenance.

## 7. Alternative flows
- **5a. Filter by state or berth type:** the list is filtered client-side from the same data.

## 8. Exception flows
- **3a. Connection lost:** warning shown; automatic reconnect; on reconnect the client reloads the snapshot.

## 9. Business rules
- **BR-1** State is derived at query time (schema §4): `Bảo trì` if an active maintenance interval contains now; `Đang sử dụng` if an approved plan contains now and its voyage is `BERTHED`; `Đã đặt trước` if an approved plan starts later; `Trống` otherwise.
- **BR-2** State changes only through business events (approve, berth, depart, maintenance). The screen never sets a state.
- **BR-3** An `OUT_OF_SERVICE` berth shows as out of service, regardless of plans.

## 10. Acceptance criteria
- AC-1 A change is visible within 5 seconds. **Partly passed:** a catalog change reaches an open page within 5 s without reload (integration: hint received; e2e: row appears). Events from plan approval, berthing, departure and maintenance cannot be verified until those use cases exist. A state that changes only with time (a plan starting) is caught by the 60 s reload, not by an event.
- AC-2 The state matches the derived rule for each of the four states. **Passed** (unit: precedence; integration: free, reserved, in use, maintenance, out of service, late vessel, vessel still berthed after the plan end, pending plan, future and cancelled maintenance; e2e: states shown and filtered).
- AC-3 Connection loss shows the warning and recovers. **Passed** for an unreachable channel (e2e: the warning appears, the browser retries, the warning disappears and the list is reloaded, including a change made while disconnected). A stream cut in the middle was not simulated; it goes through the same error handler.

## 11. Assumptions and open items
| ID | Item | Rationale | Affected |
|---|---|---|---|
| A-1 | Server-Sent Events are used only to refresh the view; they are not proof of delivery. | Legacy P1 doc, critical gap G9. Decision D6. | Section 6 |
| A-2 | "Bảo trì" state for this delivery comes from data only (maintenance intervals can be seeded or created by a later milestone). | UC-034 UI is out of scope. | BR-1 |
| A-3 | `OUT_OF_SERVICE` is an operational state outside the four display states; it is shown as a fifth label. | The specification lists four states. An out-of-service berth is not one of them. Needs approval. | BR-3 |
| A-4 | An approved plan that holds the berth now while its voyage has not berthed yet shows `Đã đặt trước` (the schema text only says "starts later"; otherwise the berth would look free for a late vessel). | The berth is still reserved for that vessel. | BR-1 |
| A-5 | A voyage that is BERTHED keeps the berth `Đang sử dụng` after the plan end until it departs. | Same idea as UC-022 A-2: use follows the actual berthing. | BR-1 |
| A-6 | Pending plans (not yet approved) never reserve a berth in the display; they are listed in the berth detail. | Spec BR-1 names approved plans. | BR-1 |
| A-7 | Refresh hints are sent by an in-process channel, so they work for one API process. The client also reloads every 60 s and on reconnect. | ADR-001 single node; SSE is a hint only (A-1). | Section 6 |

## 12. Demo scenario
1. Show all berths as `Trống`. Approve a plan starting in one hour. Expect `Đã đặt trước` within 5 s.
2. Berth the vessel at the planned time. Expect `Đang sử dụng`.
